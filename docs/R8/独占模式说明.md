# R8（RuoYi-Cloud）独占模式说明

> 2026-11-01 实测结论。R8 是 21 座靶场里**唯一无法与其他靶场共存**的一座。

## 一、为什么必须独占

R8 不是单个 jar，而是 **7 个 JVM**：

| 组件 | 堆上限 | Metaspace |
|---|---|---|
| ruoyi-auth | 384 MB | 192 MB |
| ruoyi-modules-system | 512 MB | 224 MB |
| ruoyi-modules-gen | 384 MB | 192 MB |
| ruoyi-modules-job | 384 MB | 192 MB |
| ruoyi-modules-file | 384 MB | 192 MB |
| ruoyi-gateway | 448 MB | 224 MB |
| **小计** | **2496 MB** | **1216 MB** |
| Nacos（zip 形态） | — | 约 512 MB |
| **合计** | | **约 4.2 GB** |

本机 16GB。典型靶场占用：R6 413MB、R10 296MB、RocketMQ 255MB、
jmreport 175MB、gen 162MB、R11 149MB、thymeleaf 146MB、R7 113MB、R1 110MB、R2 102MB。
跑 10 座站就是 **1.9GB**。

R8 的 4.2GB + 靶场的 1.9GB + 操作系统/IDE ≈ 超出 16GB。

## 二、预检会挡住什么

`start_r8_cloud.py` 有内存预检（`R8_MIN_FREE_MB`，默认 3200MB），不足时：

1. 打印需要多少 / 现有多少
2. 给出独占模式的正确命令
3. 列出占用最高的 java，并**区分靶场进程与外部 java**

第 3 条是 2026-11-01 加的。之前只笼统说「内存不足」，用户会去停靶场 ——
而实测本机最大的单一占用者是 **VS Code 的 Java 语言服务器（1.2GB）**，
比任何一个靶场站点都大。预检现在会明说「这部分停靶场腾不出来」。

## 三、正确的独占流程

```bash
cd "C:\Users\HZR\Desktop\若依系统"

# 1. 停掉所有靶场
python scripts\lab.py down site component middleware special

# 2. 需要的话关掉 VS Code 的 Java 扩展（或整个 VS Code）
#    实测它常驻 1.2GB，是预检失败的最常见原因

# 3. 起 R8
python scripts\start_r8_cloud.py start

# 4. 扫描（19108）
python main.py -u http://127.0.0.1:19108 --report artifacts/blind_v2/r8-cloud

# 5. 用完立刻停 —— 不停的话其他靶场起不来
python scripts\start_r8_cloud.py stop
```

## 四、在盲测矩阵里的定位

R8 标 **EXCLUSIVE**，不参与常规批量扫描：

- 常规矩阵：R1–R7、R9–R12 + C1/C2/C3/C4/D1/A2
- 独占轮次：单独跑 R8，跑完即停
- 报告里必须写明「R8 为独占轮次，与其他站点不同批次」

这样 R8 不占常规批次的内存，也不会因为内存不足被静默跳过
（上一轮报告里的 `SKIP_LOW_MEM` 既不算通过也不算失败，是最差的状态）。

## 五、已知历史问题

（WinError 10013）。解法是管理员执行 `net stop winnat && net start winnat`。

```
R8 全部就绪: ['ruoyi-auth', 'ruoyi-modules-gen', 'ruoyi-modules-file',
              'ruoyi-modules-system', 'ruoyi-modules-job', 'ruoyi-gateway']
gateway pid -> http://127.0.0.1:19208/  (nginx: http://127.0.0.1:19108/)
Nacos 服务注册数: 6
19108 首页: 200「智谷园区运营平台」
```

停掉后释放约 1.4GB（1866MB → 3186MB 空闲）。

> 起不来的最常见原因不是靶场占内存，而是 **VS Code 的 Java 语言服务器常驻 1.2GB**。
> 预检现在会明确区分「靶场进程」与「外部 java」。

### 扫描结果与两条重要发现

`main.py -u http://127.0.0.1:19108` → 6 条 CONFIRMED，但：

**发现 1：`cms=""`，variant 也为空 —— 这是正确的，不是缺陷。**

根路径是无框架特征的 SPA（品牌化成「智谷园区运营平台」），favicon 是
`eeed0dd225e44a5fe7b5f31fea185b61`（5561B），**不是**若依原版
`e49fd30ea870c7a820464ca56a113e6e`（16958B）。

按 0.7 的决策（R1 保原版 favicon 作基线、其余站品牌化），R8 属于被品牌化的那批。
所以「认不出」是必然结果 —— 这正好量化了「识别链路对单一特征的依赖有多脆」。

**发现 2：检出的是 gateway 的 actuator，不是若依业务漏洞 —— 归因问题。**

`/prod-api/actuator/env` 与 `http://127.0.0.1:19208/actuator/env`（gateway 直连）
**响应完全一致** —— 网关把 `/prod-api/**` 全转给了自己。

实际检出的 6 条：

| 条目 | 归属 |
|---|---|
| Spring Boot Actuator H2 Console 未授权 | gateway 的 actuator |
| Spring Boot Actuator 未授权访问（env） | gateway 的 actuator |
| Swagger API 文档泄露 | gateway 的 `v3/api-docs`（`info.title = "OpenAPI definition"`） |
| RuoYi Swagger 未授权访问 | 同上 |
| 未授权访问（批量） | 同上 |
| RuoYi-Plus 认证接口探测 | gateway 路由的 `/prod-api/auth/login` |

**这些是真阳性**（gateway actuator 确实未授权暴露，是真实风险），
但报告把它们挂在「若依 Swagger / RuoYi-Plus」名下，会让人误以为是若依业务系统的问题。
盲测报告里要按「gateway 组件暴露」归类。

### 未测到的部分（诚实记录）
