## 二、按需启动与资源

| 组合 | 大致内存 | 适用 |
|---|---|---|
| 单站（R1–R7/R9–R11） | 0.3–0.8 GB | 单点验证 |
| R8（Nacos + 6 服务） | ~3.2 GB | 需先停掉部分站点；启动脚本会预检，内存不足直接拒绝 |
| C1 四组件 | ~1.2 GB | 组件类插件 |
| C2 三组件 | ~1.0 GB | Spring 专项插件 |
| D1 / A2 / C3 | 各 0.4–0.6 GB | 二开 / 认证 / 误报 |

原则：**用到谁启动谁**。所有启停脚本都只操作自己，不写"全量启动"。

## 三、每类测什么

| 类别 | 靶场 | 核心问题 |
|---|---|---|
| 版本曲线 | R1–R5 | 4.5.1→4.8.3 的插件版本过滤是否准确 |
| 变体识别 | R6–R10 | Vue / Cloud / Plus / Jeecg 能否区分 |
| 负样本 | R11、R5、R10 | 非若依目标、安全基线、相近框架是否误报 |
| 组件 | C1 / C2 | actuator / Jolokia / H2 / Data REST / Config / SBA / Spring4Shell / Cloud Function |
| 二开 | D1 | 离开官方特征后还能不能识别、登录链能否适配 |
| 欺骗 | C3 | 假 .git/.env/备份/Druid/Swagger 会不会被当成真漏洞 |
| 认证降级 | A2 | 双因子挡住时是否诚实判 UNKNOWN、是否静默回退 |

## 四、2026-10-31 基线里已记录的扫描器缺口

1. **D1**：`cms=""`、0 CONFIRMED。二开形态（context-path + 改登录地址 + 换 favicon + 去版本号）完全识别不出；`--auth-login` 仍在打 `/login`。
2. **C3**：5 条 CONFIRMED，其中 4 条 A 类（假文件确实存在），1 条 **B 类硬误报**：
   `Swagger API 文档泄露` 在 `paths={}` 的情况下仍判泄露。
3. **A2**：`report.json` 没有 `auth_status` 字段；`--auth-login` 失败后静默回退匿名扫描，退出码 0。
   用户会误以为"已认证扫过"。
4. **C2**：SBA 真服务在 19311，`/applications`、`/instances` 有 JSON，插件未命中；
   SCF 被指纹误判成 `ruoyi-cloud`，并带一条 Swagger 误报。
5. **R8**：Cloud 变体/ Nacos / Gateway 可测；`gateway actuator health` 因 Windows Redis INFO 兼容问题关闭了 redis 健康子项（已写入 `docs/R8/部署说明.md`）。

## 五、目录约定

```
src/<编号>/            源码（R1–R12、C1、C2、C3、D1、A2）
build/<站点>/          构建产物
runtime/<站点>/        运行目录、日志、前端部署
nginx/conf.d/*.conf    入口配置（D1/A2 的 conf 会随启停改名启用/停用）
scripts/               启停与自检脚本
reports_c2/ reports_c3/ reports_d1/ reports_a2/   各靶场基线扫描结果
docs/                  工单与站点说明
```
