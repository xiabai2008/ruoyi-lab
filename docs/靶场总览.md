## 二、统一入口：`scripts/lab.py`

**起停和体检都走它**，不要用 `netstat` + 人眼判断"起没起来"。

```bash
python scripts\lab.py status              # 全量体检：入口码 + 后端端口 + 业务探针
python scripts\lab.py up R2 C1-2          # 按依赖顺序启动（自动带上 MySQL/Redis/Nginx）
python scripts\lab.py down R2             # 停止
python scripts\lab.py verify site         # 严格断言：任一不 UP 就退出码 1
python scripts\lab.py clean               # 清「PID 文件在但进程已死」的残留
python scripts\lab.py logs                # 列出各站 run.log 体积，超 100MB 标红
python scripts\lab.py clean-logs          # 批量清空超阈值日志
python scripts\lab.py manifest            # JSON：git tag/commit/dirty + 每站状态
python scripts\lab.py urls site           # 只输出 HTTP 入口，一行一个
```

状态口径：

| 状态 | 含义 |
|---|---|
| `UP` | 入口可访问 + 后端端口监听 + 业务探针返回预期码 |
| `DEGRADED` | 入口在但后端没监听（典型：Nginx 502）**——这种站扫了也是白扫** |
| `DOWN` | 入口不在 |

**为什么需要这一层**：曾遇到「Nginx 在 LISTENING、后端已死、扫描器卡 17 分钟一直重试」，
`netstat` 看起来一切正常。`lab.py status` 能当场报出来。

## 五、目录约定

```
src/<编号>/            源码（R1–R12、C1、C2、C3、C4、D1、A2）  ← 不进 git（上游检出 4.9G）
  └── C4/              C4 是自己写的靶场源码                    ← 进 git
build/<站点>/          构建产物                                 ← 不进 git
runtime/<站点>/        运行目录、日志、前端部署                  ← 不进 git
  └── C4/              C4 的运行配置（redis.conf 等）            ← 进 git（jar 除外）
lab_assets/            真实感诱饵（遗留 SQL、漏删的 .git 等）    ← 进 git
nginx/conf.d/*.conf    入口配置（D1/A2 的 conf 随启停改名）      ← 进 git
nginx/html/            错误页（含 WAF 403 页）                   ← 进 git
scripts/               启停与自检脚本（含 lab.py）                ← 进 git
seed/ db/              业务数据种子与建库脚本                     ← 进 git
.state/                修复脚本与 SQL（pid/日志不进 git）         ← 进 git
docs/                  站点说明与设计文档                         ← 进 git
```

## 六、版本控制

靶场是一个 git 仓库，只跟踪「人与配置」，产物目录全部忽略。

```bash
cd <工程根>
git tag                      # lab-v1 起的一系列基线
git log --oneline
```

**做对比实验前先冻结版本**：

```bash
git tag lab-vN
python scripts\lab.py manifest > artifacts/lab_manifest.json
```

`manifest` 会把 `git describe --tags --always` 和 `git status --porcelain` 一起写进去，
报告引用它就能回答"那次实验用的是哪一版靶场、当时工作区脏不脏"。

> 注意：`manifest` 的 `dirty` 字段会把 D1/A2 的 nginx conf 改名显示为变更 ——
> 那是启停脚本的正常行为，不是未提交的代码改动。

## 七、真实性资产

靶场里有一类文件不是构建产物、也不是配置，而是**人为造的历史遗留**：

| 站点 | 资产 | 说明 |
|---|---|---|
| R1 | `static-extra/docs/ry_20210415.sql` | 运维遗留的建库脚本（`/docs/**` 在 Shiro 匿名清单里，真实可匿名下载） |
| R6 / R7 | `ui/.git/` | 前端构建时漏删的 .git（Nginx 根路径直出静态文件，匿名可读） |
| R7 | `ui/.svn/` `ui/.idea/` | SVN→Git 迁移时漏删 |

这些放在顶层 `lab_assets/`，由 `scripts/lab_assets.py` 铺到 `runtime/` 下，
`lab.py up` 时自动执行。

**为什么不直接放进 `runtime/`**：R7 的诱饵就是个 `.git` 目录，直接放会被外层
git 当成 submodule（`adding embedded git repository`）。而且 `runtime/` 语义是
"可重建产物"，掺人为资产会模糊这个语义。
