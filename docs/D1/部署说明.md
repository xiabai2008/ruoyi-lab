# D1 邕江物流运输管理系统 · 部署说明

## 一、定位

D1 是 RuoYi 4.6.2 单机版的二开变形站，用来测量扫描器在“不像官方若依”时的识别能力。

- 源码：`src/D1`（复制自 `src/R2`，排除 `target/`、`.git/`）
- 数据库：`ry_d1`（由 `ry_r2` 导出，表结构未改）
- JDK：8（`D:\develop\java-se-8u44-ri`）
- 产物：`build/D1/ruoyi-admin.jar`
- 访问入口：Nginx `19321` → 后端 `19221`
- 启停：`python scripts\d1_start.py start|stop|status`
- 漏洞演示模式：默认 safe，`python scripts\d1_start.py start vuln` 开启（详见
  [漏洞演示模块.md](漏洞演示模块.md)）

## 二、路径与地址

| 项目 | 值 |
|---|---|
| `server.port` | `19221` |
| `server.servlet.context-path` | `/portal` |
| 站点根入口 | `http://127.0.0.1:19321/` → 302 → `/portal/` |
| 登录页 | `GET /portal/auth/signin` |
| 登录提交 | `POST /portal/auth/signin` |
| 旧登录地址 | `/login`、`/portal/login` 均已移除，返回 404（不跳转） |

Shiro 的 `loginUrl` 已改为 `/auth/signin`；旧地址不再有控制器映射，仅保留匿名透传规则以确保返回 404，
否则请求会落到 `/** = user` 而被 302 到新登录页。

Nginx 只转发 `/portal/` 前缀，且不做 URI 重写：

```nginx
location = / { return 302 /portal/; }
location = /portal { return 302 /portal/; }
location /portal/ { proxy_pass http://127.0.0.1:19221; }
```

## 三、登录返回结构

登录接口与框架其它接口不同，这是本次二开的核心变量：

- 登录成功：`{"success": true, "message": "登录成功"}`
- 登录失败：`{"success": false, "message": "用户不存在/密码错误"}`（HTTP 200）
- 登录页 `static/ruoyi/login.js` 以 `result.success === true` 判定成功

其它接口保持 RuoYi 原生结构，未做改造：

- 列表：`{"total": N, "rows": [...], "code": 0, "msg": "..."}`
- 普通结果：`{code, msg, data}`

列表接口（如 `/portal/system/user/list`）仍只接受 **POST**，与 4.6.2 原生一致。
带会话用 GET 请求会由框架统一异常处理返回 `{"msg":"不支持' GET'请求","code":500}`（HTTP 200），
不是 405；这是原生行为，不是本站改动。

## 四、验证码关闭（有意的控制变量）

`application.yml` 中：

```yaml
shiro:
  user:
    captchaEnabled: false
```

这是**有意为之的对照设计**，不是配置遗漏：

- R2 保留验证码，作为“官方形态”的对照；
- D1 关闭验证码，专门隔离“改 context-path / 改登录地址 / 改返回结构”这一个变量；
- 关闭后登录页不渲染验证码框，`admin/admin123` 可直接登录，便于自动化复现。

## 六、启停行为

- `start`：校验 19221 空闲 → JDK8 启动 jar → 等 `/portal/auth/signin` 200 → 启用
  `nginx/conf.d/D1.conf` 并 reload → 等 19321 200 → 写 `.state/D1.pid`
- `stop`：按 PID 结束 → 等 19221 释放 → 把 `D1.conf` 改名为 `D1.conf.disabled` 并 reload →
  等 19321 释放 → 删 PID
- 只操作 D1；Nginx reload 为平滑重载，不影响 R1–R12 / C1 / C2 站点
- 环境变量 `SERVER_PORT`、`SERVER__PORT` 在启动前清除，避免 Spring relaxed binding 劫持端口

## 七、基线

- 有效基线：`reports_d1/anon_v2/`，目标 `http://127.0.0.1:19321/`
- 旧基线 `reports_d1/anon/` 产生于入口未修复时，仅作对照保留，不作为测量结论

## 八、漏洞演示模式（v1.5.5 新增）

D1 在 RuoYi 4.6.2 二开代码上新增了一块**可开关的漏洞演示模块**，用于给扫描器
「定时任务 RCE（未授权访问）」「代码生成模块 SSTI」两个插件做真实站点验收：

```bat
python scripts\d1_start.py start vuln   :: 漏洞版：/openapi/** 进 Shiro anon 白名单 + 模板求值
python scripts\d1_start.py start safe   :: 默认 safe：官方鉴权行为，两插件不 CONFIRMED
python scripts\d1_start.py status       :: 会打印当前 lab.mode
curl http://127.0.0.1:19321/portal/lab/status   :: {"site":"D1","labMode":"safe|vuln"}
```

- 二开 Java 源码跟踪在 `lab_src/D1_ruoyi_vuln/`，用 `python scripts\d1_vuln_install.py` 铺进 `src/D1`；
- nginx 的 `conf.d/D1.conf` 增加 2 条精确路径的网关兼容映射（`/monitor/job/edit`、
  `/tool/gen/preview/*` → `/portal/openapi/**`），老路径形态不变；
- safe 模式不改变登录、默认口令、二开路径等既有能力；
- 设计、验收记录与**限制**（官方生成器链路不可触发插件假设的 SSTI、扫描器不识别
  `/portal` context 等）见 [漏洞演示模块.md](漏洞演示模块.md)。
