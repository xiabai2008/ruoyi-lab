# D1 · 邕江物流运输管理系统 · 漏洞演示模块

> 目标：让扫描器 2 个「此前零检出」的 RuoYi 插件在**真实 RuoYi 4.6.2 二开应用**上各命中 1 次：
>
> 1. 定时任务 RCE（未授权访问）—— `plugins/ruoyi/job_rce.py`
> 2. RuoYi 代码生成模块 SSTI —— `plugins/ruoyi/ruoyi_gen_rce.py`
>
> 同时保证默认（safe）模式仍是官方鉴权行为：两插件均不得 CONFIRMED，
> D1 的登录（`/portal/auth/signin`）、默认口令真阳性（`admin/admin123`）、二开路径保持不变。

## 一、为什么不只是「加一个 Controller」

D1 是 RuoYi 4.6.2 二开：应用挂在 `/portal` context-path 下，登录入口改成
`/portal/auth/signin`、登录返回结构也做了二开。扫描器插件按 RuoYi 原生根路径
（`/monitor/job/edit`、`/tool/gen/preview/1`）探测，**根路径本身不会命中后端**。

因此本模块同时包含两块「真实二开」内容：

1. **Java 侧**：二开新增「内部运维开放接口」`/portal/openapi/**`（任务维护 + 代码预览），
   供外部运维平台免登录调用；接口自身没有 `@RequiresPermissions` 权限注解，
   安全边界只剩 Shiro 的 `/** = user` 统一登录拦截。
2. **Nginx 侧**：二期把开放接口迁到 `/portal/openapi/**` 后，网关为「改版前老路径」
   保留 2 条精确路径的兼容映射（等价于运维在网关做 URI rewrite）：
   `/monitor/job/edit`、`/tool/gen/preview/*`。

漏洞版（`lab.mode=vuln`）在 Shiro 过滤链里把 `/openapi/**` 加进 **anon 白名单** ——
复刻真实项目「为了免登录对接，把接口路径塞进 Shiro 白名单」的配置疏漏。白名单一开，
开放接口就绕过鉴权直达真实业务层。

safe 模式（默认）**不加**白名单，两条老路径经网关映射到后端后仍被 Shiro
302 拦截到 `/portal/auth/signin`；且开放接口方法内部还有一份 `labMode` 判定，
即便带着会话调用也返回「开放接口未启用」、不执行业务、不求值模板。

## 二、模拟的两类真实疏漏

| # | 疏漏 | 真实世界对应 | 影响 |
|---|---|---|---|
| 1 | Shiro anon 白名单误配：`/openapi/**` 进 anon | 为对接内部运维平台「免登录」，把接口路径加入白名单，误以为网关/内网会兜底 | 开放接口全网匿名可达 |
| 2 | 开放接口无权限注解，只依赖 Shiro URL 鉴权 | 二开接口只写业务代码、未加 `@RequiresPermissions` | 一旦 URL 层放行即无任何鉴权 |
| 3 | 代码预览的「表名模板」把用户可控值当模板求值 | 二开为分表场景支持动态表名（`${...}` 表达式），直接当模板源码渲染 | 模板注入（真实表达式求值） |

## 三、模式开关

默认 **safe**；以下任一方式开启 **vuln**：

```bat
:: 方式 1：d1_start.py 直接指定（推荐，启停一体）
python scripts\d1_start.py start vuln
python scripts\d1_start.py start --lab-mode vuln

:: 方式 2：环境变量（lab.py 的 --lab-mode 就是通过 LAB_MODE 透传的）
set LAB_MODE=vuln && python scripts\d1_start.py start
python scripts\lab.py up D1 --lab-mode vuln

:: 方式 3：手工 java 启动时传 JVM 参数（等价 -Dlab.mode=vuln）
java -Dlab.mode=vuln -jar build\D1\ruoyi-admin.jar ...

:: 方式 4：Spring profile
... --spring.profiles.active=druid,prod,vuln
```

- 开关实现：`com.ruoyi.framework.lab.LabMode`（`@Component`，读 `lab.mode` 配置 /
  `vuln` profile，默认 safe）。
- 运行时自检：`GET http://127.0.0.1:19321/portal/lab/status` →
  `{"site":"D1","labMode":"safe"}` / `{"site":"D1","labMode":"vuln"}`（两种模式都放行，只回模式）。
- `python scripts\d1_start.py status` 会打印当前 lab.mode。

## 四、漏洞面与两种模式的行为

### 4.1 定时任务 RCE（未授权访问）

探针（扫描器原样）：`POST /monitor/job/edit`，表单
`jobId=99999&jobName=...&invokeTarget=ryTask.ryNoParams&cronExpression=0/10 * * * * ?`

| 模式 | 实际请求链 | 响应 | 扫描器判定 |
|---|---|---|---|
| vuln | nginx `/monitor/job/edit` → 后端 `/portal/openapi/monitor/job/edit` → Shiro anon → `LabOpenApiJobController` → 真实 `ISysJobService` | HTTP 200 `{"code":500,"msg":"任务不存在"}` | **CONFIRMED**（未鉴权进入业务层） |
| safe | nginx 映射不变 → Shiro `/** = user` 拦截 | 302 `/portal/auth/signin` → 200 登录页 | UNKNOWN（登录墙拦截，非 CONFIRMED） |

- 控制器复刻官方 `SysJobController.editSave` 的业务校验（Cron 合法性、rmi 调用目标拦截），
  再调用真实服务层；`jobId=99999` 不存在时在业务层返回「任务不存在」，**不会修改任何任务**。
- safe 模式下 Shiro 会先拦截，正常用户仍可按原路径修改任务，行为不受影响。

### 4.2 RuoYi 代码生成模块 SSTI

探针（扫描器原样）：`GET /tool/gen/preview/1?tableName=sys_user`（基线）与
`?tableName=sys_user_${7*7}`（注入），差分判定「基线无 49 / 注入有 49 / 无原文回显」。

| 模式 | 实际请求链 | 响应 | 扫描器判定 |
|---|---|---|---|
| vuln | nginx `/tool/gen/preview/1` → 后端 `/portal/openapi/tool/gen/preview/1` → Shiro anon → `LabOpenApiGenController` | 基线 `{"code":0,"data":{"tableName":"sys_user",...}}`；注入 `{"code":0,"data":{"tableName":"sys_user_49",...}}` | **CONFIRMED**（差分成立，模板真实求值） |
| safe | 同上映射 → Shiro `/** = user` 拦截 | 302 `/portal/auth/signin` | SAFE/UNKNOWN（非 CONFIRMED） |

- 求值实现：Spring SpEL 的 `TemplateParserContext("${", "}")`，对 `tableName` 参数做
  **真实表达式求值**（`${7*7}` → `49`），不是字符串替换、不是打桩。
- 同时调用真实 `IGenTableService.selectGenTableById/previewCode`：库表存在时返回官方
  Velocity 渲染结果（本靶场 `gen_table` 未导入数据，故返回「业务表未导入」提示）。
- **注意：这是二开新增的求值面，不是 RuoYi 官方生成器链路的注入面**，原因见第七节「限制」。

## 五、代码结构与改动清单

```
lab_src/D1_ruoyi_vuln/java/
├── com/ruoyi/framework/lab/
│   └── LabMode.java                    # 模式开关：lab.mode / vuln profile，默认 safe
└── com/ruoyi/web/lab/
    ├── LabStatusController.java        # GET /lab/status 运行模式自检
    ├── LabOpenApiJobController.java    # POST /openapi/monitor/job/edit（真实任务服务）
    └── LabOpenApiGenController.java    # GET /openapi/tool/gen/preview/{id}（真实生成器 + SpEL 求值）
```

安装脚本：`python scripts\d1_vuln_install.py`（`--check` 只比对，`--uninstall` 回滚）。
`.gitignore` 忽略 `src/*`，所以 Java 源码跟踪在 `lab_src/`，由脚本铺进 `src/D1`：

| 源（lab_src） | 目标（src/D1） |
|---|---|
| `com/ruoyi/framework/lab/*.java` | `ruoyi-framework/src/main/java/com/ruoyi/framework/lab/` |
| `com/ruoyi/web/lab/*.java` | `ruoyi-admin/src/main/java/com/ruoyi/web/lab/` |

同时给 `ruoyi-framework/.../config/ShiroConfig.java` 打 3 处补丁（脚本幂等，原始文件备份为
`ShiroConfig.java.lab-orig`）：

1. 注入 `LabMode`；
2. `/lab/status` 固定 anon（运行模式自检，两种模式都在 Shiro 墙前应答）；
3. `lab.mode=vuln` 时 `filterChainDefinitionMap.put("/openapi/**", "anon")`。

Nginx：`nginx/conf.d/D1.conf`（停站时为 `D1.conf.disabled`）新增 2 条网关兼容映射
（精确路径，原因见 7.4）。

Maven 依赖零新增：SpEL 来自 D1 已带的 `spring-expression`（Thymeleaf/AOP 传递依赖），
无需改 pom。

## 七、限制与扫描器侧发现（只报告，未改 ruoyi-scan）

### 7.1 官方 RuoYi 4.6.2 生成器链路**无法**触发插件假设的 `tableName` SSTI

- 官方 `GenController.preview` 只接收 path 变量 `tableId`，**不读取 `tableName` 查询参数**；
  表名来自 `gen_table` 库记录。
- 官方模板引擎是 **Velocity 1.7**，实测（用项目 `.m2` 里的 velocity-1.7 直接跑
  `Velocity.evaluate`）：
  ```
  IN=[${7*7}]            OUT=[${7*7}]      # 原样输出，不求值
  IN=[sys_user_${7*7}]   OUT=[sys_user_${7*7}]
  IN=[#set($x=7*7)$x]    OUT=[49]           # 只有 #set 指令里的算术会求值
  ```
  且原样输出还含 `7*7` 原文，会直接违反插件的「无载荷回显」条件。
- 结论：插件注释里「preview 的 tableName 参数进 Velocity 渲染」这一注入面在官方
  4.6.2 代码里不存在。若验收口径要求「必须走官方 Velocity 链路」，该项在真实
  RuoYi 4.6.2 上不可实现（不是配置问题）。D1 的命中来自二开开放接口对
  `tableName` 的 SpEL 模板求值（真实引擎求值、非打桩），已在 4.2 明确标注。

### 7.2 扫描器不识别 `/portal` 上下文，插件探针落 404（D1 需要用网关兼容映射）

- `core/basepath.detect_api_base` 只试探 `/prod-api`、`/dev-api`、`/api`、
  `/jeecg-boot`、`/jeecg` 这几个固定候选；`plugin_target` 不会使用
  `core/auth_chain` 已经发现的 `base_path=/portal`。
- 直接 `main.py -u http://127.0.0.1:19321` 时，插件探针
  `/monitor/job/edit`、`/tool/gen/preview/1` 在根路径只会命中 nginx 404，
  D1 的这两个插件**永远探测不到后端**（基线报告即如此）。
- 靶场侧处理：`nginx/conf.d/D1.conf` 增加 2 条精确路径网关兼容映射（与 R10 的
  `/jeecg-boot/jeecg-boot/*` 双前缀归一同类），报告里插件 URL 仍是老路径。
- 建议扫描器：把 auth_chain 已发现的 `base_path` 传给插件探测基准，或让
  `detect_api_base` 支持「根路径 302 到同源目录」的通用推导（`_discover_context_base`
  已有该能力，只是没接到 plugin_target）。

### 7.3 gen 插件 `requires_auth=True` 与匿名命中互相矛盾（报告口径不一致）

- `ruoyi_gen_rce` 声明 `requires_auth = True`，但它的差分探针实际走匿名会话；
  本次 `-u` 扫描（无 `--auth-login`）中差分证据成立，随后被 orchestrator 的
  「认证纪律」降级为 UNKNOWN：
  `report.json` 里是 UNKNOWN + evidence「未取得高权会话…原证据：差分验证成立…」。
- 但 CLI 在降级**之前**打印 `[*]存在RuoYi 代码生成模块 SSTI`，与报告状态不一致
  （用户会以为已确认，报告里却是无法判定）。
- 建议：评估该插件是否真的需要高权会话（它探的 preview 端点可匿名可达）；
  或让 CLI 打印最终落盘状态；或在这类「匿名可达」场景给插件单独标注。

### 7.4 nginx 兼容映射必须用精确路径，不能偷懒映射整个前缀

实测踩坑：最初把 `/monitor/` 整前缀映射到 `/portal/openapi/monitor/`，导致根路径
`/monitor/job/list` 从 404 变成 302，于是 auth_chain 的上下文前缀发现
（`_discover_context_base` → 受保护接口探测）在 `base=""` 就命中 302、不再推导
`/portal`，默认口令插件的受保护接口取证退化为「登录成功但取不到业务数据」→
**D1 的默认口令真阳性丢失**。改为只映射 2 条精确老路径后恢复正常。
后续改 D1 的 nginx 配置时不要扩大映射范围。

### 7.5 D1 指纹

D1 因 `/portal` 上下文，根路径指纹本来就识别不到 RuoYi（`cms` 为空）；
本次改动前后基线/safe/vuln 三份报告指纹一致（`cms:"" confidence:0.0`），属既有形态，
不是本模块引入的回归。

## 八、扫描器验收（2026-11-02，scanner ruoyi-scan v1.5.5 工作区）

```bat
:: vuln（任务要求的命令）
python main.py -u http://127.0.0.1:19321 --report artifacts/d1_wp4_vuln
:: vuln（补认证，用于让 requires_auth 插件保留 CONFIRMED）
python main.py -p http://127.0.0.1:19321 --auth-login admin:admin123 --report artifacts/d1_wp4_vuln_auth
:: safe（默认模式）
python main.py -u http://127.0.0.1:19321 --report artifacts/d1_wp4_safe
python main.py -p http://127.0.0.1:19321 --auth-login admin:admin123 --report artifacts/d1_wp4_safe_auth
```

### 8.1 vuln 模式（两插件全部命中；默认口令真阳性保持）

| 插件 | `-u`（任务命令） | `-p --auth-login admin:admin123` | 证据（report.json 原文摘要） |
|---|---|---|---|
| 定时任务 RCE（未授权访问） | CONFIRMED | CONFIRMED | `未鉴权进入业务层：code=500 msg=任务不存在` |
| RuoYi 代码生成模块 SSTI | UNKNOWN（差分证据成立但被认证纪律降级） | **CONFIRMED** | `差分验证成立：基线 tableName=sys_user 无求值结果，注入 tableName=${7*7} 后响应出现独立数字 49（模板已求值）` |
| 后台默认口令（admin/admin123） | CONFIRMED | 不加载（brute 类） | `默认口令登录成功…受保护接口取到业务数据：/portal/system/user/list 返回 rows=26 total=26` |

### 8.2 safe 模式（0 CONFIRMED，站点能力不变）

| 插件 | safe `-u` | safe `-p --auth-login` | 实际行为 |
|---|---|---|---|
| 定时任务 RCE（未授权访问） | UNKNOWN | UNKNOWN | 登录墙：302 → `/portal/auth/signin` → 200 登录页 |
| RuoYi 代码生成模块 SSTI | UNKNOWN（原判 SAFE，认证纪律降为 UNKNOWN） | SAFE | 状态码 404（`/tool/gen/edit` 根路径不存在） |
| 后台默认口令（admin/admin123） | CONFIRMED（与基线一致） | 不加载 | 登录页 200，`admin/admin123` 真阳性保持 |

> 两模式对比：safe 的 CONFIRMED 集合 = {默认口令}，vuln 的 CONFIRMED 集合 =
> {定时任务 RCE, 代码生成 SSTI, 默认口令}；safe 未新增任何 CONFIRMED。

### 8.3 D1 现有能力回归

- `python scripts\lab.py status D1` → `[OK] 入口19321=ok 后端19221=ok /portal/auth/signin=200`；
- `GET /portal/auth/signin` → 200，`admin/admin123` 登录 → `{"success":true,"message":"登录成功"}`；
- `/portal/lab/status` 两种模式都返回当前模式，不影响业务接口；
- 默认口令插件输出与基线一致（受保护接口仍能取到 26 条用户数据）；
- 站点指纹与基线一致（`cms:""`）。
