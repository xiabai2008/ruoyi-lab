# R10 · JeecgBoot 漏洞演示模块

> 目标：让扫描器 8 个 JeecgBoot 插件在**真实 JeecgBoot 3.6.3 应用**上各命中 1 次，
> 同时保证默认（safe）模式仍是 3.6.3 的修复后行为，不污染负样本语义。

## 一、为什么不是「加一个 Controller」

8 个插件探测的路径里有 7 个**已经被 JeecgBoot / 积木报表自己的 Controller 占用**：

| 路径 | 占用方 |
|---|---|
| `/sys/login`（POST） | `LoginController.login` |
| `/sys/dict/list`（GET） | `SysDictController.list` |
| `/sys/user/queryUserByDepId`（GET） | `SysUserController.queryUserByDepId` |
| `/jmreport/list`、`/jmreport/upload`、`/jmreport/testConnection`、`/jmreport/queryFieldBySql` | `jimureport-spring-boot-starter 1.7.2-beta` |

再声明同路径 `@RequestMapping` 会在启动期直接 `Ambiguous mapping` 失败。
因此演示行为放在一个 **Servlet Filter（`LabVulnerabilityFilter`）** 里，
按「精确路径 + 精确 HTTP 方法」接管，未命中请求原样放行；
过滤器顺序在 Shiro/JWT 之前，vuln 模式下匿名请求才能绕过鉴权墙抵达演示逻辑。

模块代码（Java，随 `jeecg-system-biz` 打进 `jeecg-system-start` fat jar）：

```
lab_src/R10_jeecg_vuln/
├── java/org/jeecg/modules/lab/
│   ├── LabMode.java                 # 模式开关：lab.mode 属性 / spring profile vuln，默认 safe
│   ├── LabModuleConfig.java         # 注册 Filter（HIGHEST_PRECEDENCE + 20）
│   ├── LabVulnerabilityFilter.java  # 8 个端点的路由与直接应答 + /lab/status
│   └── LabVulnerabilityService.java # 8 个漏洞的 Java 实现（真实库/真实写盘/真实引擎求值）
└── resources/lab/etc-passwd         # Windows 下 /etc/passwd 夹具（Linux 部署走真实文件）
```

安装到源码树：`python scripts\r10_vuln_install.py`（`.gitignore` 忽略 `src/`，
所以 Java 源码放 `lab_src/` 跟踪，由脚本铺进 `src/R10`）。
安装后目标位置：

```
src/R10/jeecg-module-system/jeecg-system-biz/src/main/java/org/jeecg/modules/lab/
src/R10/jeecg-module-system/jeecg-system-biz/src/main/resources/lab/
```

## 二、模式开关

默认 **safe**；以下任一方式开启 **vuln**：

```bat
:: 方式 1：lab.py（推荐，启停一体）
python scripts\lab.py down R10
python scripts\lab.py up R10 --lab-mode vuln

:: 方式 2：launch.py 直接透传 Spring 参数
python scripts\launch.py R10 --lab.mode=vuln

:: 方式 3：环境变量
set LAB_MODE=vuln && python scripts\launch.py R10
```

也可用 Spring profile：`--spring.profiles.active=dev,vuln`。
运行时自检：`curl http://127.0.0.1:19110/jeecg-boot/lab/status` 返回 `{"labMode":"safe|vuln"}`。

## 三、端点与两种模式的行为

| # | 插件 | 请求 | vuln 模式行为 | safe 模式（3.6.3 官方） |
|---|---|---|---|---|
| 1 | JeecgBoot 默认口令 | `POST /sys/login` `{"username":"admin","password":"123456","code":"","checkKey":""}` | 服务端按官方算法补验证码进 Redis 后**真走 LoginController**，返回真实 token | 验证码无效（HTTP 200 + `{"message":"验证码无效"}`） |
| 2 | 字典越权 | `GET /sys/dict/list?current=1&size=10` | 匿名返回 `sys_dict` 真实分页（records/total） | Shiro 拦截：HTTP 401 `Token失效` |
| 3 | 任意文件读取 | `GET /common/download?fileName=../../../../../../etc/passwd` | 真实路径穿越读取；Windows 主机无 /etc/passwd 时返回内置 passwd 夹具 | Shiro 拦截：HTTP 401 |
| 4 | jmreport 文件上传 | `POST /jmreport/upload` multipart（file+biz） | 解析 multipart，文件真实写入 jeecg 上传根目录，返回 fileName/url | 积木报表鉴权墙：`Token校验失败，无权限访问！` |
| 5 | 报表 SSTI | `POST /jmreport/testConnection` 的 `connUrl` 含 `${7*7}` | 用 **FreeMarker 2.3.32 真实渲染** connUrl，响应 JSON 含 49 | 鉴权墙（同上） |
| 6 | 报表未授权 | `GET /jmreport/list?current=1&size=10` | 匿名返回 `jimu_report` 真实分页 | 鉴权墙（HTTP 200 + `{"code":500,...,"message":"Token校验失败，无权限访问！"}`） |
| 7 | jmreport SQL 注入 | `POST /jmreport/queryFieldBySql` `{"sql":"select user()","dbKey":"master"}` | **真实 JDBC 执行**任意 SQL，返回 `user()` 结果（如 `root@localhost`）；SQL 报错原样回显 | 鉴权墙 |
| 8 | queryUserByDepId SQL 注入 | `GET /sys/user/queryUserByDepId?depId=1' and extractvalue(...)-- ` | 复刻修复前实现：depId 字符串拼接进 SQL，MySQL 报 `XPATH syntax error: '~root@localhost'` | Shiro 拦截：HTTP 401（3.6.3 已改为 `id` 参数 + 参数绑定） |

> safe 模式下 `/lab/status` 仍可访问（只返回模式信息），其余 8 个端点完全保持官方行为。

### 7.3 扫描器侧发现（只报告，未改 ruoyi-scan）

1. **`-p` 与「8 插件」目标不自洽**：`cli/runner.py` 的 `MODE_CATEGORIES` 中
   `"p": ["vuln"]`，而 `plugins/jeecgboot/default_password.py` 的 `category = "brute"`，
   所以验收命令 `-p ... --auth-login admin:123456` 永远不会执行默认口令插件（报告里 MISSING），
   最多 7/8。建议验收改用 `-u`，或评估把该插件 category 调成 vuln（属产品口径决策）。

2. **JeecgBoot 目标被 API base 双前缀**：`core/orchestrator.py` 的 API 前缀探测把
   `plugin_target` 提升为 `http://host/jeecg-boot/`（`core/basepath.py` 的 Jeecg 探针命中），
   而 JeecgBoot 专项插件内部又写死 `/jeecg-boot/...`，于是 5 个插件的实际请求 URL 变成
   `/jeecg-boot/jeecg-boot/...`（见 r10_vuln 报告里 SSTI/两个 SQLi/文件读取/报表未授权的 url）。
   真实 JeecgBoot 目标同样会因此漏报。
   本靶场在 `nginx/conf.d/R10.conf` 加了一条路径归一（`/jeecg-boot/jeecg-boot/*` → `/jeecg-boot/*`）
   作为兼容，扫描器侧建议：对 jeecgboot 包不追加 api_base，或插件统一先判断 target 是否已带 context-path。

3. **jmreport 列表插件分页口径与字典插件不一致**：`plugins/jeecgboot/jmreport_list_unauth.py`
   复用 `dict_unauth._is_dict_list_json`，要求 **顶层** `records/rows` + `total/success`；
   而 `dict_unauth` 自己的 `_is_dict_page` 支持 `result.records` 包装。
   积木报表常见响应是 `{"result":{"records":...}}`，按现有口径会漏报（本轮靶场按插件口径返回
   顶层分页字段后命中）。建议两个插件统一使用能解包 `result` 的判定函数。
